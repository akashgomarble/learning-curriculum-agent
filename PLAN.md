# Learning Curriculum Builder — Implementation Plan

RapidCanvas Senior AI Engineer take-home, round 2. Author: Akash Gupta. Due Sun 8 Nov 2026 (plan written Fri 6 Nov).

Scope of this file: the *plan*, not the implementation. It records the research done, the empirical checks run from this laptop, the architecture, the evaluation design (the centerpiece), the test set, the build order, and the README outline. The recruiter asked that LLM calls go through OpenRouter; nothing here depends on any other model provider.

---

## 0. TL;DR

- **Pipeline**: plan sub-topics and queries (Sonnet 5.5) → discover candidates with `yt-dlp` flat search (no key) → hydrate transcripts with `youtube-transcript-api` (+ `yt-dlp` caption fallback) → per-video structured assessment on a windowed transcript with evidence quotes (Haiku 5.5, parallel) → topic-overlap dedup (free, from assessment labels) → budget-constrained selection, ordering and reasoning (Sonnet 5.5) → JSON + Markdown with per-pick confidence, evidence quotes, a dropped list, and near-duplicate explanations.
- **Cost / latency (projected from measurements)**: ≈ $0.06–0.10 and ≈ 45–70 s per curriculum, cold. Per-video assessments are cached by `video_id`, so repeated topics get cheaper.
- **Evaluation**: three layers — (1) deterministic checks that need no LLM (budget fit, hallucinated IDs, constraint violations, known-topic leakage, unknown-topic coverage, ordering, redundancy, *quote verifiability* of every reason against the real transcript); (2) an LLM judge from a *different model family* than the curator (OpenAI `gpt-5.6-terra`), binary per-criterion with critiques, plus position-swapped pairwise comparisons against two baselines (top-N-by-views, no-transcript ablation); (3) a human-label pass (binary pass/fail + critique, Hamel-style critique shadowing) on every output, reported as Cohen's κ, TPR/TNR and a disagreement table. EVAL.md will also say what the eval does *not* measure and which signals were discarded.
- **Empirical check (this machine, Fri 6 Nov)**: 4 parallel searches → 36 unique candidates in 5 s; 25/36 transcripts fetched in 12 s with 4 workers (median 1.3 s each); zero IP blocks across ~60 transcript and ~15 search requests; failures were 10 Hindi-only auto-caption videos (not translatable) and 1 `TranscriptsDisabled`. Live OpenRouter structured-output call on Haiku 5.5 succeeded in 3.0 s and returned `usage.cost`.

## 2. Research findings (with sources)

### 2.1 Getting YouTube data without an API key

**`yt-dlp` 2026.10.26** (installed and tested; [README](https://github.com/yt-dlp/yt-dlp#readme)):
- `ytsearchN:<query>` with `extract_flat=True` returns N entries in ~1–2 s per query. Flat entries contain exactly: `id, title, duration, view_count, channel, channel_id, channel_url, uploader, description, thumbnails, url, _type, ie_key`. **No** `upload_date`, `like_count`, `chapters`, or captions in flat mode. Playlists appear in results too (`id` starting with `PL…`, `duration=None`) and must be filtered out (or expanded, see §8).
- Full `extract_info(url)` (~3.5 s/video) adds `like_count, upload_date, channel_follower_count, categories, tags, language, chapters[{title,start_time,end_time}], subtitles, automatic_captions` (157 auto-caption languages on the sample video; `en` available as `json3/srv1/srv2/srv3/ttml/srt/vtt`).
- Captions can be downloaded without the video: `skip_download=True, writeautomaticsub=True, subtitleslangs=["en.*"], subtitlesformat="json3"` (tested: 3.0 s, 331 words, matches the transcript API output).
- Warnings seen: "No supported JavaScript runtime (deno)" and "no impersonate target" — these only affect *format* extraction, not metadata/captions. We never need formats, so they are harmless; README will say so.
- YouTube search-result URLs with the `sp=` filter param are accepted by yt-dlp, but the duration-filter mapping I tried did not behave as documented (the "long >20 min" value returned 8–19 min videos). Since `duration` is free in flat results, **filter duration client-side** instead.
- `gl=US&hl=en` on the search URL did **not** change the geo-skew of results (see §2.4). The extractor arg `youtube:lang=en` only affects translated *metadata*.
- Bot-check / "Sign in to confirm you're not a bot" is overwhelmingly a datacenter-IP problem (yt-dlp issue [#10128](https://github.com/yt-dlp/yt-dlp/issues/10128); [Render thread](https://community.render.com/t/yt-dlp-sign-in-problem/26692)); cookies (`cookiefile`) or PO tokens (`youtube:po_token=CLIENT.CONTEXT+TOKEN`) are the documented workarounds. Not needed from a laptop; documented as the production risk.

**`youtube-transcript-api` 1.2.5** (installed and tested; [README](https://github.com/jdepoix/youtube-transcript-api)):
- v1.x is instance-based: `api = YouTubeTranscriptApi(proxy_config=None, http_client=None)`; `api.fetch(video_id, languages=["en"])` → `FetchedTranscript` (`.snippets[i].text/.start/.duration`, `.is_generated`, `.language_code`, `.to_raw_data()`); `api.list(video_id)` → `TranscriptList` with `find_transcript / find_manually_created_transcript / find_generated_transcript(languages)`; `Transcript.translate(code)` only when `is_translatable`.
- Exceptions to handle: `IpBlocked` (HTTP 429 on timedtext), `RequestBlocked`, `TranscriptsDisabled`, `NoTranscriptFound`, `VideoUnavailable`, `AgeRestricted`. IP bans hit cloud IPs mostly; the README recommends rotating residential proxies (`WebshareProxyConfig`) or `GenericProxyConfig(http_url, https_url)`; cookie auth is currently broken upstream.
- Measured: median 1.3 s/fetch, ~171 words per video-minute (min 87, max 235). A 60-min video ≈ 10k words ≈ 13–14k tokens; the longest hit (an 11.5 h course) was 85,918 words. **Transcripts must be windowed before any LLM call.**
- Auto-generated transcripts dominate (18/25 OK fetches were auto). Auto captions lack punctuation and mis-transcribe product names ("Vite" → "white"), which the assessment prompt must be told about.

**YouTube Data API v3** (optional path, not used in v1): default 10,000 units/day; `search.list` costs 100 units (→ 100 searches/day), `videos.list` 1 unit per call of up to 50 IDs, and `captions.download` requires the *owner's* OAuth scope, so it cannot fetch third-party transcripts at all ([getting started](https://developers.google.com/youtube/v3/getting-started), [quota table](https://developers.google.com/youtube/v3/determine_quota_cost)). Conclusion: the official API is a fine *metadata* source at scale but cannot replace scraping for transcripts; it's a README "with more time" item.

### 2.2 OpenRouter (verified live against `/api/v1/models` on 6 Nov)

| Model | $/M in | $/M out | cache read $/M | ctx | structured outputs |
|---|---|---|---|---|---|
| `anthropic/claude-sonnet-5.5` | 2.00 | 10.00 | 0.10 | 1M | yes |
| `anthropic/claude-haiku-5.5` | 0.10 | 0.50 | 0.01 | 1M | yes |
| `anthropic/claude-opus-5.5` | 4.00 | 20.00 | 0.20 | 1M | yes |
| `google/gemini-3.8-flash` | 0.825 | 4.125 | 0.083 | 1M | yes |
| `openai/gpt-5.6-terra` | 2.00 | 12.00 | 0.20 | 1M | yes |
| `openai/gpt-5.6-luna` | 0.20 | 1.20 | 0.02 | 1M | yes |

- All six advertise `response_format`, `structured_outputs`, `tools`, `reasoning`. Request shape per the [structured outputs doc](https://openrouter.ai/docs/guides/features/structured-outputs): `response_format={"type":"json_schema","json_schema":{"name":…,"strict":true,"schema":…}}` plus `provider={"require_parameters": true}` so routing only hits endpoints that honor the schema. Enforcement is per-endpoint ("some guarantee, some treat as a strong hint"), so the client still validates with pydantic and retries once on failure.
- `usage: {"include": true}` returns `usage.cost` (USD), token counts, and `cached_tokens` — this is how the cost analysis will be measured rather than estimated. Verified: a Haiku 5.5 strict-schema call returned `{"topics":[…],"is_project_based":true}`, provider=Anthropic, 285 in / 38 out tokens, cost $0.0000475, 3.0 s.
- No embedding models are exposed on `/models` with this key, so dedup is done locally (§3.6).
- Keys: `OPENROUTER_API_KEY` (own, for development) and `OPENROUTER_API_KEY_RC` (recruiter, $20 cap) in `.env`; the code reads `OPENROUTER_API_KEY` only, and the README tells the grader to put their key in that variable. Development runs use my own key; the final recorded runs use the recruiter key so the cost numbers in EVAL.md are what they would see.
- Environment gotcha found during testing: python.org's macOS Python has no CA bundle (`CERTIFICATE_VERIFY_FAILED`). The `openai` SDK (httpx + certifi) avoids it; the README notes it anyway.

### 2.3 Prior art on curriculum / learning-path generation

- **YT-Pilot** (Albassam et al., arXiv [2604.03543](https://arxiv.org/abs/2604.03543), Apr 2026): turns YouTube videos into a persistent, pathway-aware learning structure; LLM ordering prompt groups videos by concept and requires non-decreasing Bloom levels; evaluated by a 20-person within-subjects study on *perceived* goal clarity and coherence. Takeaway: prerequisite ordering and concept grouping are the structural signals; outcome measurement is still self-report even in research.
- **Education-oriented Graph RAG for learning-path recommendation** (arXiv [2506.22303](https://arxiv.org/abs/2506.22303), 2025): combines prerequisite and similarity relations between knowledge concepts. Takeaway: make the "sub-topic plan" an explicit, ordered list of concepts with prerequisite edges, and select videos *against* it rather than ranking videos directly.
- **LLM Agents for Education survey** (arXiv [2503.11733](https://arxiv.org/abs/2503.11733)): curricula are built either retrieval-based or generation-based. Ours is retrieval-based with a generated plan — the plan is the thing the eval can check coverage against.
- Recommender set-level metrics worth borrowing: intra-list diversity / topic diversification (Ziegler et al., WWW 2005), coverage of a target distribution ("calibrated recommendations", Steck, RecSys 2018). We adapt these as *unknown-topic coverage* and *pairwise topic-overlap* (§5.2).

### 2.4 Failure modes observed or documented

| Failure | Observed? | Handling |
|---|---|---|
| Geo-skewed search: from an Indian IP, generic queries return many Hindi-language videos (10/36 candidates in test 3) | **Yes** | Over-fetch (6 queries × 10), then drop candidates whose transcript language ≠ persona language; record the drop reason. Add concrete English anchor terms to queries. Documented as a reproducibility caveat: graders in the US will see a different candidate pool. |
| Hindi auto-captions are `is_translatable=False`, 0 translation languages | **Yes** | Cannot auto-translate; drop unless the persona wants Hindi (persona 6). |
| `NoTranscriptFound` / `TranscriptsDisabled` | **Yes** (1/36 disabled) | Fall back to `yt-dlp` auto-caption download; if still nothing, keep the candidate as *metadata-only* with `assessment.evidence_source="metadata"` and a mandatory confidence penalty; selector is told it may only pick such a video if nothing transcript-backed covers the sub-topic. |
| Manual transcript that is a machine translation of a Hindi video (`is_generated=False`, lang=`en`, "So how are you my dear friends…") | **Yes** | Language ID on the transcript text itself (cheap heuristic: Haiku returns `spoken_language` in the assessment; the English stopword ratio is a free pre-check). |
| Playlists and Shorts in search results | **Yes** | Drop `_type=="playlist"`/`PL…` ids and `duration < 120 s` before hydration (Shorts can't be a curriculum item; "in 100 seconds" content is excluded by the constraint anyway and additionally by a title regex). |
| Very long transcripts (85k words) | **Yes** | Chapter-aware windowing (§3.4). |
| IP block (`IpBlocked`/`RequestBlocked`) | **No** (0 in ~60 fetches at 4 workers) | Exponential backoff, cap concurrency at 4, disk cache so re-runs never re-fetch; `proxy_config` hook via env vars; committed fixture snapshots of the test-set candidate pools so graders can run the eval offline (`--offline`). |
| Non-JSON-serializable `extract_info` output | documented | `ydl.sanitize_info()` before caching. |

### 2.5 Evaluation literature used

- Zheng et al., *Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena* (arXiv [2306.05685](https://arxiv.org/abs/2306.05685)): position, verbosity and self-enhancement bias; swap order in pairwise judging; ~80% judge–human agreement is the realistic ceiling.
- Ye et al., *Justice or Prejudice? Quantifying Biases in LLM-as-a-Judge* (ICLR 2025, arXiv [2410.02736](https://arxiv.org/abs/2410.02736)): twelve bias types; rubric vagueness is a dominant failure.
- Panickssery, Bowman & Feng, *LLM Evaluators Recognize and Favor Their Own Generations* (NeurIPS 2024, arXiv [2404.13076](https://arxiv.org/abs/2404.13076)): motivates judging with a different model family than the curator.
- Dubois et al., *Length-Controlled AlpacaEval* (arXiv [2404.04475](https://arxiv.org/abs/2404.04475)): control for output length — relevant because a curriculum with longer reasons may look "more grounded".
- Liu et al., *G-Eval* (arXiv [2303.16634](https://arxiv.org/abs/2303.16634)): chain-of-thought rubric evaluation; we use the form-filling style but binary.
- Hamel Husain, [*Creating a LLM-as-a-Judge That Drives Business Results*](https://hamel.dev/blog/posts/llm-judge/): one domain expert, binary pass/fail with written critiques (not Likert), ~30 examples to start, iterate the judge prompt until it agrees with the expert, report TPR/TNR separately because raw agreement is misleading on imbalanced labels, and treat the judge as a tool for finding failure modes rather than a dashboard.
- ALCE (Gao et al., 2023, arXiv [2305.14627](https://arxiv.org/abs/2305.14627)) citation precision/recall via entailment, and RAGAS faithfulness (Es et al., 2023, arXiv [2309.15217](https://arxiv.org/abs/2309.15217)): the model for our *grounding* metric — each claim in a reason must be supported by the transcript; we make the cheap version deterministic (quote verifiability) and the expensive version an LLM entailment check.
- Cohen's κ with the Landis & Koch (1977) bands (0.41–0.60 moderate, 0.61–0.80 substantial); practitioner notes ([1](https://dev.to/maya_andersson_dev/your-llm-as-judge-eval-set-is-too-small-here-is-the-math-2iac), [2](https://dev.to/maya_andersson_dev/calibration-set-size-for-llm-as-judge-when-50-traces-is-enough-and-when-200-is-mandatory-d1d)) agree that below ~100 labels κ has a CI of roughly ±0.15 — which is exactly the honesty caveat EVAL.md must carry.
- Dedup: SemDeDup (Abbas et al., arXiv [2303.09540](https://arxiv.org/abs/2303.09540)) for embedding-based near-dup clustering; MinHash/Jaccard for cheap set overlap.

### 2.6 Extra discovery sources (bonus) — is it worth it?

- **Reddit**: unauthenticated `.json` endpoints have returned 403 since late May 2026, `old.reddit.com` included, and new API keys are no longer issued ([dev.to write-up](https://dev.to/tonywangca/why-reddit-blocked-unauthenticated-json-in-2026-and-how-to-still-get-reddit-data-58b9)). **Skip.**

Cheap to add as a *query-expansion* source: search `"best youtube tutorial <goal>" site:reddit.com OR site:news.ycombinator.com` and feed the mentioned channel/video names into the YouTube query list. ## 3. Architecture

### 3.1 Pipeline

```
persona.json
   │
   ▼
[1] PLAN  (Sonnet 5.5, structured)        → LearningPlan: ordered sub-topics w/ prerequisites, per-sub-topic
   │                                         budget share, 5–7 search queries, exclusion rules derived from
   │                                         known/constraints, feasibility note (e.g. "45 min is not enough for X")
   ▼
[2] DISCOVER (yt-dlp flat, parallel)      → ~50–70 raw entries → prefilter (dedupe ids, drop playlists, shorts,
   │                                         duration > budget, title-regex exclusions) → ~30–40 Candidates
   ▼
[3] HYDRATE (transcript API, 4 workers)   → transcript (lang, generated?), chapters from description timestamps,
   │                                         cache on disk by video_id; metadata-only fallback
   ▼
[4] ASSESS  (Haiku 5.5, parallel, cached) → per-video VideoAssessment: topics_covered, level, is_project_based,
   │                                         project_described, tools/versions mentioned, teaching style, spoken
   │                                         language, 2–4 verbatim evidence quotes w/ timestamps, relevance to each
   │                                         sub-topic (0–3), red flags (outdated API, pure theory, "100 seconds")
   ▼
[5] DEDUP   (pure Python)                  → clusters of candidates with topic-set Jaccard ≥ 0.6 and same level;
   │                                         clusters are passed to the selector with an instruction to pick ≤1 per
   │                                         cluster and explain why
   ▼
[6] SELECT  (Sonnet 5.5, structured)      → Curriculum: ordered picks (video, sub-topic(s), reason citing quote ids,
   │                                         confidence 0–1 + why, watch_from/until if a chapter is enough),
   │                                         total_minutes, dropped[] with reasons, near_duplicates[] explanations,
   │                                         feasibility warnings, assumptions made for ambiguous goals
   ▼
[7] VERIFY + RENDER (pure Python)          → assert every cited quote exists in the transcript (fuzzy ≥ 0.85),
                                             budget arithmetic, IDs ∈ pool; write runs/<persona>/curriculum.json,
                                             curriculum.md, trace.json (all prompts, raw outputs, usage.cost, timings)
```

Stage [1] runs once; [2]–[4] are embarrassingly parallel; [6] sees only the assessments (not transcripts), which keeps its prompt ≈ 8–12k tokens.

### 3.2 Model per stage and why

| Stage | Model | Why |
|---|---|---|
| Plan | `claude-sonnet-5.5` | Needs judgment about prerequisites, feasibility and what the learner's `known` list implies. One call, small. |
| Assess | `claude-haiku-5.5` | 30–40 calls × ~6k tokens; $0.10/M makes this ≈ $0.02–0.03 per run. The task is extraction/classification with quotes — Haiku-shaped. 1M context means no truncation pressure, but we window anyway for cost. |
| Select | `claude-sonnet-5.5` | The one place "taste" matters: trading off coverage, budget, redundancy and the learner's constraints, and writing legible reasons. Opus 5.5 is 2× the price for a stage that is ~$0.03; kept as a CLI flag (`--selector-model`) for the model-comparison bonus. |
| Q&A (bonus) | `claude-sonnet-5.5` | Reads the saved trace; cheap. |
| Judge | `openai/gpt-5.6-terra` | Different family from the curator (self-preference, §2.5). `gemini-3.8-flash` as a second judge for the model-comparison runs where the curator itself is OpenAI. |
| Grounding entailment | `openai/gpt-5.6-luna` | Narrow NLI-style task, cheap, different family. |

Temperature 0 everywhere; `seed` passed where supported; still non-deterministic, so stability is *measured*, not assumed (§5.2).

### 3.3 Structured output strategy

- Every LLM call: pydantic model → `model_json_schema()` → `response_format=json_schema(strict=true)` + `provider.require_parameters=true` + `usage.include=true`.
- One helper, `llm.chat_json(model, system, user, schema_cls, max_tokens) -> (obj, Usage)`: validates with pydantic; on `ValidationError`/JSON error retries once with the error message appended; on HTTP 429/5xx retries with exponential backoff (3 attempts, 2/4/8 s); 60 s timeout per call. Records `cost_usd`, tokens, latency into a run-scoped ledger.
- Prompts live in `curriculum/prompts/*.md` with `{placeholders}` so the reviewer can read them without reading Python. Few-shot examples are *not* included in prompts for the reference persona (to avoid overfitting to the graded case); the assessment prompt gets one generic example of a good evidence quote.
- Quotes are addressed by id (`q1..q4`) from the assessment, so the selector cannot invent quotes — it can only cite ones Haiku extracted, and stage [7] verifies those against the transcript.

### 3.4 Transcript windowing (keeps Haiku input ≈ 4–6k tokens)

Given ~171 words/min:
- ≤ 25 min: full transcript.
- > 25 min: first 4 min (intro/outline), then one 90-second window at the start of each chapter (chapters from `yt-dlp` or description-timestamp regex `(\d{1,2}:)?\d{1,2}:\d{2}`), else 8 evenly spaced 90-second windows; last 2 min (wrap-up/what was built). Each window is prefixed with its `mm:ss` so quotes keep timestamps.
- Hard cap 5,000 words. Multi-hour "complete course" videos get a `watch_from/watch_until` recommendation from the selector when a chapter suffices, counted at chapter length toward the budget.

### 3.5 Caching, retries, timeouts

- `.cache/videos/<id>.json`: metadata + transcript (+ `fetched_at`). `.cache/assessments/<id>.<prompt_hash>.<model>.json`. `.cache/search/<sha(query)>.json` (TTL 7 days so re-runs are reproducible but not stale forever).
- `fixtures/<persona_id>/` committed: the exact candidate pool used for the recorded runs, so `uv run curriculum eval --offline` reproduces EVAL.md numbers without YouTube access. (Gitignored `.cache/` stays local.)
- YouTube calls: 4-worker thread pool, 20 s timeout, 3 retries with backoff on transient errors, no retry on `TranscriptsDisabled`/`NoTranscriptFound`.
- Whole-run budget guard: abort the run if the ledger exceeds `MAX_RUN_USD` (default 0.50) — protects the recruiter's $20 cap.

### 3.6 Dedup (bonus "content-level deduplication", done cheaply)

Three options were weighed:
1. Transcript embeddings (SemDeDup-style): needs an embedding model; none on OpenRouter here, local `sentence-transformers` adds a 90 MB dependency. Overkill for 30 candidates.
2. LLM pairwise (Haiku): 30 candidates → 435 pairs; even clustered it's ~$0.05 extra and slow.
3. **Topic-set overlap from the assessment we already paid for**: each assessment yields `topics_covered` (normalized short strings) and `level`; Jaccard ≥ 0.6 with the same level → same cluster. Zero extra cost, explainable ("both cover: Vite setup, useState, map/keys, localStorage"). TF-IDF cosine over transcripts (scikit-learn, tiny) is the tie-breaker when topic lists are short.

Picked (3). The selector receives clusters and must output `near_duplicates: [{kept, dropped, shared_topics, why_kept}]`.

### 3.7 Rough cost per curriculum (cold cache)

| Stage | Calls | Tokens in / out (est.) | USD |
|---|---|---|---|
| Plan (Sonnet) | 1 | 1.5k / 0.8k | 0.011 |
| Assess (Haiku) | ~32 | 6k / 0.5k each | 0.027 |
| Select (Sonnet) | 1 | 10k / 2.5k | 0.045 |
| Verify/render | 0 | — | 0 |
| **Total** | | | **≈ 0.08** (range 0.06–0.10) |

Eval side per persona: judge rubric (terra, ~12k/1.5k) ≈ $0.04; 2 pairwise comparisons × 2 orders ≈ $0.10; grounding entailment (luna) ≈ $0.01. Full eval over 8 personas × (agent + 2 baselines) ≈ $2–3; the model-comparison runs ≈ $2 more. Comfortably inside the $20 cap with my own key used for iteration.

Latency (measured components): search 2–5 s (parallel) + hydrate ~12 s (36 videos, 4 workers) + assess ~8–12 s (32 parallel Haiku calls, each ~3–6 s, 8 workers) + plan ~8 s + select ~20–30 s ⇒ **≈ 50–65 s cold, ≈ 30 s warm**.

## 5. Evaluation design (EVAL.md — the centerpiece)

### 5.1 Principles

1. Decide "good" *before* looking at outputs: each persona ships with an `expectations` block written while authoring the persona, and the deterministic checks read it.
2. Prefer checks that cannot be gamed by the curator's prose: a reason is "grounded" only if its quote is actually in the transcript.
3. Binary labels with critiques, not Likert scores (Hamel; Ye et al.). Anything scored 1–10 by an LLM is decoration.
4. A judge from a different family than the curator; pairwise with position swap; length-controlled where length could leak.
5. Measure the judge against a human (me) and *publish the disagreements*, not just κ.
6. Say loudly what is not measured.

### 5.2 Layer 1 — deterministic checks (no LLM, run on every output)

| Metric | Definition | Pass rule |
|---|---|---|
| `schema_valid` | output parses into `Curriculum` | must |
| `no_hallucinated_videos` | every `video_id` ∈ candidate pool of this run | must |
| `budget_fit` | `total_minutes ≤ budget` | must |
| `budget_utilisation` | `total_minutes / budget` | report; persona-specific floor (default ≥ 0.6; tiny budgets ≥ 0.5) |
| `pick_count_in_range` | within persona `expectations.pick_count` (default 3–8) | soft |
| `constraint_violations` | count of picks matching the persona's `expectations.forbidden_title_regex` or `forbidden_assessment_flags` (e.g. `surface_intro`, `pure_theory`, `wrong_language`) | 0 |
| `known_topic_leakage` | picks whose assessed `primary_topics` ⊆ persona `known` (normalized) | 0 |
| `unknown_coverage` | fraction of persona `unknown` items covered by ≥1 pick's `topics_covered` (string-normalized match, synonyms table per persona in expectations) | report; floor from expectations (default ≥ 0.8) |
| `order_violations` | pairs (i<j) where pick i's sub-topic has pick j's sub-topic as a prerequisite in the plan; plus assessed `level` decreasing by ≥2 steps | 0 |
| `redundancy` | max pairwise topic-set Jaccard among picks | ≤ 0.6 |
| `quote_verifiability` | fraction of evidence quotes found in the real transcript (rapidfuzz `partial_ratio ≥ 85` within ±60 s of the stated timestamp) | ≥ 0.9; a pick with 0 verified quotes is a hard fail |
| `metadata_only_picks` | picks whose assessment had no transcript | report (should be 0 unless the pool forced it) |
| `dropped_list_nonempty` / `near_dup_explained` | legibility requirements from the brief | must / must when a cluster existed |
| `stability@3` | mean Jaccard of pick sets across 3 runs on the same fixture | report |
| `cost_usd`, `latency_s` | from the ledger | report |

Layer 1 alone catches the embarrassing failures (made-up videos, blowing the budget, picking "React in 100 seconds", picking a JS-basics video). It cannot tell whether the chosen project tutorial is *good*.

### 5.3 Layer 2 — LLM judge (different family: `gpt-5.6-terra`)

**Rubric judge (pointwise, binary per criterion, with critique).** Input: persona, the curriculum JSON, and for each pick the assessment summary *and* the verified quotes (so the judge grades against content, not titles). Criteria (each `pass|fail` + one-sentence critique):
- `tailored`: would this ordering/selection change materially for a different background? (generic lists fail)
- `content_grounded_reasons`: reasons cite what is taught, not views/length/channel
- `goal_mirroring`: ≥1 pick builds something structurally like the goal (for build-goals)
- `prereq_order_sensible`
- `constraints_respected`
- `dropped_reasons_sound`: the dropped list would survive a learner asking "why not X?"
- `overall_would_recommend`: the holistic question a mentor would answer

**Pairwise judge (position-swapped).** Agent vs each baseline on the same persona and candidate pool: "Which curriculum better serves this learner within the budget?" Run both orders; disagreement ⇒ tie (Zheng et al.). Reasons are truncated to the same length in both arms (length control).

**Baselines**
- `top_n_by_views`: the plan's queries, flat search, sort by views, greedily fill the budget, reason = metadata template. The "search and view count don't solve this" claim from the brief, operationalized.
- `no_transcript_ablation`: the full pipeline with transcripts replaced by title+description (`--no-transcripts`). Isolates how much the content layer buys.
- (If time) `metadata_only_selector`: Sonnet sees only titles/descriptions/durations — a stronger ablation that separates "LLM judgment" from "transcript evidence".

**Grounding entailment (`gpt-5.6-luna`)**: for each reason sentence, is it entailed by the transcript windows + verified quotes? Reported as `reason_faithfulness` (RAGAS-style fraction). This is the expensive complement to `quote_verifiability`: a quote can be real while the reason over-claims.

### 5.4 Layer 3 — human labels and judge–human agreement

Protocol (critique shadowing, adapted):
1. I label every curriculum produced for the 8 personas × {agent, top_n_by_views, no_transcript} = 24 curricula, ~110 picks, *before* reading judge outputs. Per curriculum: `overall_pass` + critique. Per pick: `pick_pass` + critique (is this the right video for this slot for this learner?). Labels stored in `eval/labels/human_labels.jsonl`, with a `labelled_at` timestamp and the run hash.
2. Run the rubric judge on the same items; compute Cohen's κ for `overall_would_recommend` vs `overall_pass` (n=24) and for `pick_pass` (n≈110), with a 1,000-sample bootstrap CI; also raw agreement, TPR and TNR with the human as ground truth (Hamel: agreement alone is misleading when one class dominates).
3. Produce the **disagreement table**: every item where judge ≠ human, with both critiques and my adjudication of who is right. This is the section the brief calls "where the eval and human judgment disagree".
4. Iterate the judge prompt at most twice on a 6-curriculum dev slice; freeze; report the held-out numbers. State plainly that n is small, that the labeller is the author, and that κ CIs will be ±0.15–0.2 wide.

Expected (to be replaced by measured): κ in the 0.4–0.7 band; judge more lenient than me on `tailored`, stricter on `prereq_order`.

### 5.5 Model / prompt comparison (bonus)

- Selector model: Sonnet 5.5 (default) vs Opus 5.5 vs `gpt-5.6-terra` vs `gemini-3.8-flash`, same fixtures, same assessments. Report Layer-1 metrics, pairwise win-rate judged by a model *not* in the comparison arm (gemini judges when OpenAI is the curator), cost and latency.
- Prompt strategy: "select directly" vs "plan-then-select" (ablate stage 1 by letting the selector infer sub-topics). Hypothesis: planning improves `unknown_coverage` and `order_violations` at +$0.01.
- Each comparison is one `compare` command; results land in a second table in EVAL.md.

### 5.7 What the evaluation does NOT tell you (to be written honestly in EVAL.md)

- Whether the learner achieves the goal. No outcome data; everything is a proxy for "a mentor would pick this".
- Teaching quality: pacing, audio, code correctness on screen, whether the Vite version shown still works. Transcripts show *what* is covered, not *how well*.
- Generalization beyond 8 author-written personas; hidden personas may hit failure modes (sparse topics, non-English, hardware/hands-on goals) the test set under-represents.
- The judge's agreement with *one* human who also built the system; κ on n≈110 has a wide CI; a second labeller would be the first thing to add.
- YouTube search is non-deterministic and geo-personalized; the committed fixtures freeze *my* candidate pool, not the one a grader in another country will get. The eval measures selection quality given a pool more than discovery quality.
- Costs are OpenRouter list prices on one day; latency is one laptop on one network.

### 5.8 Signals considered and discarded (with the reason)

| Signal | Why discarded |
|---|---|
| View count / likes as quality | Ranks popularity, not fit — the brief's premise. Kept only as a tie-breaker *within* a dedup cluster and as the baseline to beat. |
| Like/view ratio | Not in flat results (needs a 3.5 s full extract per video); noisy below ~10k views; measures entertainment as much as teaching. |
| Comment sentiment | yt-dlp `getcomments` is slow (seconds per video) and comments mostly praise the creator; would need another LLM pass per video for a weak signal. "With more time" item. |
| Channel subscriber count | Brand bias; penalizes the small channel that happens to build exactly the habit tracker. |
| Upload recency as a score | Important for tooling topics (Vite, React 19) and irrelevant for sourdough or SQL. Kept as a *flag* the assessor raises ("mentions `create-react-app`, deprecated") rather than a numeric score. |
| Words-per-minute as "density" | Measured range 87–235 wpm; confounded by accent, auto-caption dropouts, and talking speed. |
| Embedding similarity goal↔transcript as the ranker | Favors keyword-dense overview videos and penalizes long builds where the goal words appear rarely; tried mentally against the reference persona and it would rank the "every React concept in 12 minutes" video first. |
| Likert 1–10 judge scores | Not actionable, drift between runs, and the mean hides the failure mode (Hamel; Ye et al.). |
| BLEU/ROUGE against a "gold" curriculum | There is no single gold; two different good curricula share few videos. |
| Judge from the same family as the curator | Self-preference bias (Panickssery et al.). |
| Transcript language detection via a library (`langdetect`) | Extra dependency for a signal Haiku returns for free in the assessment. |

### 7.1 10K users/day projection (method; numbers filled from measurements)

- Cold cost ≈ $0.08 → $800/day uncached. Assessments are the cacheable unit (keyed by `video_id`+prompt hash): learning goals are Zipfian, so after warm-up a large share of candidates are already assessed. With a 70% assessment hit-rate: $0.08 → ≈ $0.06/run → $600/day; the remaining cost is dominated by the Sonnet selector (≈55%).
- Levers, in order: (1) cache assessments and search results (biggest, zero quality loss); (2) move the selector to a cheaper model for low-budget personas where the pool is small (measured in §5.5); (3) prompt caching on the selector's static instructions (Anthropic cache read is 10× cheaper); (4) trim the candidate pool with a cheap pre-rank (title+description Haiku pass at $0.0003/video) before transcript hydration when pools exceed 40; (5) batch endpoints (`:batch` variants exist on OpenRouter for Haiku/Gemini) for the offline warm-up.
- Non-LLM scaling is the real risk: 10K runs/day ≈ 350K transcript fetches/day from datacenter IPs — that *will* be blocked (§2.1); needs rotating residential proxies (budget line) or the official Data API for metadata plus a transcript cache with a long TTL. Latency: p50 ≈ 55 s cold is fine for a "generate a plan" UX only with streaming of stages; warm ≈ 30 s.
