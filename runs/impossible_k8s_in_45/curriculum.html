In this video, you'll learn how a Kubernetes cluster is put together. We'll look at what the control plane does, what every worker node runs, and exactly what happens after you submit a workload. Then you'll practice matching symptoms to the component most likely to cause them. You'll use that skill constantly when troubleshooting.

Let's start with the problem Kubernetes solves. Imagine running a web application in containers across 10 servers. You'd have to decide which server runs each container, restart containers when they crash, replace servers that fail, and keep track of where everything is so traffic can reach it. Doing that by hand doesn't scale. Kubernetes automates it.

You tell it what you want, for example, three copies of a web server, and it works continuously to make that true. Your description is called the desired state. The constant comparing and correcting is called reconciliation. For the exam, architecture isn't a separately scored objective, but every task depends on it. When something breaks, the first question is always the same.

What is the cluster think it should be doing? And which component is failing to make it happen?

Every cluster has two parts. The control plane makes decisions and stores the cluster's state. The worker nodes run your applications. In production, the control plane usually runs on three dedicated machines for high availability, and there may be dozens or hundreds of workers. In our lab, one control plane node and two workers are enough.

The components are the same either way. Let's start with the control plane's front door, the Kube API server. Everything in Kubernetes is an object, such as a pod or a deployment. And every read or write of an object goes through the API server. That includes requests from you, from the other control plane components,

and from every node. For each request, the API server checks who you are, which is authentication.

It checks what you're allowed to do, which is authorization. It runs admission checks that can validate or modify the request, and then it stores the result. It also lets components watch for changes so they react within moments. If the API server is down, Kube control can't reach the cluster at all. Behind the API server is ETCD, a consistent, distributed key value store.

It's the cluster's memory. Every object you create ends up there, and only the API server talks to it directly. In production, ETCD usually runs as three or five members, and it needs a majority of them, called a quorum, to accept rights. Lose ETCD without a backup, and you've lost the cluster's state.

That's why backup and restore is a core administrator task. We'll practice it in chapter three. Next, the Kube scheduler. A new pod starts without a node. The scheduler watches for those unassigned pods.

It filters out nodes that can't run a pod, for example, because they lack enough CPU or memory. Then, it scores the remaining nodes and picks the best one, and records its choice through the API server. That's called binding. The scheduler doesn't start containers; it only decides where they should run.

Then there's the Kube controller manager. It runs dozens of controllers. Each one is a small loop that watches one kind of object and corrects any difference between the desired and actual state. The deployment controller manages replica sets. The replica set controller keeps the right number of pods running.

The node controller notices when a node stops reporting. Self-healing in Kubernetes comes from these loops. On cloud platforms, a separate cloud controller manager talks to the provider, for example, to create load balancers. Our lab won't need it. Now the worker nodes. Every node runs a Kubelet, the node's agent.

The Kubelet watches the API server for pods assigned to its node. It tells the container runtime to start their containers, runs health checks, and reports status back. One detail trips people up. The Kubelet isn't a pod. It's a regular Linux service managed by system D. So when a node shows not ready, the Kubelet service on that node is one of the first things you check.

The Kubelet doesn't run containers itself. It asks a container runtime through a standard interface called the container runtime interface or CRI. The most common runtimes are Container D and Cryo, and our labs use Container D. Because the interface is standard, you can inspect containers on any node with the same tool, CRI control,

even when the API server is unavailable. Applications need stable addresses, and that's what Kubernetes services provide. On each node, Kube Proxy watches services and their endpoints, and programs packet forwarding rules, usually with IP tables or NF tables,

so traffic sent to a service reaches a healthy pod. Some network plugins, such as Cilium, can replace Kube Proxy with their own service routing. Either way, something on every node implements services. Pod networking itself, giving each pod an IP address, comes from a network plugin that uses the container network interface or CNI.

We'll install one in chapter two. And finally, the pod. A pod is the smallest unit Kubernetes runs. One or more containers that share a network address and can share storage volumes. A cluster also runs add-ons as ordinary workloads, such as Core DNS, which gives services and pods DNS names.

Now let's follow a workload from submission to running containers. Say you apply a deployment that asks for two replicas of Engine X. Deployments are covered properly in chapter seven. For now, think of one as a request for a number of identical pods.

First, Kube control sends the request to the API server, which authenticates it, authorizes it, runs admission, and stores the deployment in ETCD. Second, the deployment controller notices the new deployment and creates a replica set. Third, the replica set controller sees that two pods are wanted and none exist, so it creates two pods.

They're pending because they don't have a node yet. Fourth, the scheduler picks a node for each pod and binds it. Fifth, the Kubelet on each chosen node sees its new pod. It asks the container runtime to pull the image and start the container, and the network plugin gives the pod an IP address. Sixth, the Kubelet reports back and the pod status becomes running.

Notice that no component calls another directly. They all communicate through the API server by watching for changes. Here's that sequence in the starter cluster you'll build in video 1.3. This screen is simulated output, so your names and timings will differ.

I create the deployment with Kube control, create deployment, then list the deployment, its replica set, and its pods. Both pods are running, and the wide output shows which node each one landed on. To verify the whole chain, I list event sorted by time. Read them top to bottom. The deployment scaled up a replica set.

The replica set created the pods. The scheduler assigned each pod to a node, and the Kubelet pulled the image, created the container, and started it. That's every step from the diagram recorded by the cluster itself. Now a common failure. This pod asks for 64 CPUs, more than any node has.

Kube control get shows it's stuck in pending. When a pod is pending, describe it and read the events section. The scheduler explains itself. Zero of three nodes are available because of insufficient CPU. So the scheduler is working, the request simply can't fit.

The fix is to lower the request or add capacity. Compare that with a pending pod that has no events at all. Then the scheduler itself may not be running, which is a control plane problem. We'll troubleshoot that in chapter 17. Time to practice. Pause the video and match each symptom to the component you'd check first.

One. Kube control reports connection refused. Two. A new pod stays pending and describe shows no events at all. Three. A node shows not ready. Four. You delete a pod that belongs to a deployment and no replacement appears.

Here are my answers. Connection refused from Kube control points to the API server or to a Kube config that points somewhere wrong. A pending pod with no events points to the scheduler because nothing has even tried to place it. A not ready node points to the Kubelet on that node and then to the container runtime.

And a deleted pod that isn't replaced points to the controller manager because the replica set controller should have created a new one. Keep this mapping in mind. You'll use it in every troubleshooting chapter. Let's recap. The control plane runs the API server, ETCD, the scheduler, and the controller manager.

Every worker node runs the Kubelet, a container runtime through the CRI, and Kube proxy or an equivalent service routing implementation. Everything communicates through the API server, and controllers keep reconciling the actual state with the desired state. When a workload fails, follow the chain, stored, scheduled, started, running.

In the previous episode, we learned how to create pods manually. But, there's a big problem with standalone pods. If a pod crashes or disappears, the application can go down completely. And this is where deployments and replica sets become extremely important. A deployment allows Kubernetes to manage pods automatically.

It can keep applications running, recreate failed pods, scale applications horizontally, and perform rolling updates with almost zero downtime. On the right side, we can see the architecture. The deployment defines the desired state, in this case three replicas. Then, the replica set ensures that three pods are always running.

So, if one pod fails, Kubernetes automatically creates another one. This is one of the core ideas behind Kubernetes: self-healing and high availability. Now, we can clearly see why deployments are so important in Kubernetes. On the left side, we have self-healing. The replica set constantly checks if the desired number of pods is running.

So, if one pod crashes or disappears, Kubernetes automatically creates a new one to replace it. This is one of the most powerful Kubernetes features because applications can recover automatically without manual intervention. And on the right side, we can see horizontal scaling. Instead of running a single pod, Kubernetes can create multiple replicas of the application.

This improves availability, scalability, and traffic distribution across pods. So, deployments are not just about creating containers, they're really about keeping applications alive, scalable, and resilient automatically. In real DevOps environments, engineers constantly use the official Kubernetes documentation as reference. So, let's go to the official Kubernetes docs and grab a deployment example directly from there.

This is the official Kubernetes documentation. And here, we already have a working deployment example provided by Kubernetes itself. And this is the most important part. We only created one deployment manifest, but Kubernetes automatically created three pods based on the replicas value. Now, let's test one of the most powerful Kubernetes features: self-healing. At first, we had three running pods managed by the deployment. Then, I manually deleted one of them.

Normally, if we were working with a standalone pod, the application capacity would be reduced, and that pod would simply be gone. But watch what happened here. After deleting the pod, Kubernetes immediately noticed that the desired state was no longer satisfied. The deployment expected three replicas, but only two were running. So Kubernetes automatically created a brand new pod to replace the one we deleted.

Notice the new pod name at the bottom and its age of just a few seconds. The other two pods have been running for several minutes, while this new one was created automatically by Kubernetes. This is self-healing in action. Nobody logged into a server, nobody restarted a container, nobody manually created a replacement pod.

Kubernetes detected the problem and fixed it automatically. Self-healing is only part of the story. Another major advantage of deployments is scaling. Right now, we have three replicas running, but what happens if our application receives more traffic? Instead of manually creating more pods, we can simply tell Kubernetes how many replicas we want.

Scaling also works in the opposite direction. If traffic decreases, Kubernetes can reduce the number of running pods. Now, Kubernetes is terminating the extra pods and keeping only two replicas running. Before we finish, there's one more important capability provided by deployments: rolling updates. Imagine your application is running with three pods, and you need to deploy a new version.

Instead of stopping all pods at the same time, Kubernetes replaces them gradually. First, it creates a new pod with the updated version. Once that pod is healthy and ready, Kubernetes removes one of the old pods. Then, it repeats the process until all pods are running the new version.

This approach is called a rolling update. The major advantage is that users can continue accessing the application while the update is happening. In other words, Kubernetes can deploy new versions with little or no downtime.
